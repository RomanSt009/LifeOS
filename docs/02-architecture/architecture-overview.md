# Обзор архитектуры LifeOS

**Статус:** Черновик  
**Версия:** 0.1  
**Последнее обновление:** 2026-08-09

## Назначение

Этот документ определяет первоначальное архитектурное направление LifeOS.

Архитектура должна поддерживать:

- разработку приложения сначала для ПК;
- будущие мобильные приложения;
- будущую веб-версию;
- работу в режиме Local First;
- модульную разработку функций;
- интеграцию искусственного интеллекта;
- владение данными пользователем;
- долгосрочную поддержку и развитие проекта.

## Архитектурные цели

### 1. Кроссплатформенность

Основная бизнес-логика приложения должна быть спроектирована таким образом, чтобы платформозависимый код был изолирован.

Первоначальные платформы:

- Windows;
- macOS;
- Linux.

Будущие платформы:

- Android;
- iOS;
- Web.

### 2. Local First

Основные функции не должны зависеть от постоянного подключения к интернету.

Приложение должно уметь:

- читать локальные данные;
- создавать данные локально;
- изменять данные локально;
- выполнять поиск по локальным данным;
- работать без подключения к интернету.

Сетевые сервисы должны расширять возможности приложения, а не определять его базовую работу.

### 3. Модульная архитектура

LifeOS должен состоять из независимых модулей.

Предполагаемые модули:

Core
├── Identity
├── Storage
├── Database
├── Search
├── Entities
├── Relationships
└── Settings

Features
├── Notes
├── Tasks
├── Projects
├── Documents
├── Calendar
├── Finance
└── Contacts

Intelligence
├── AI Assistant
├── Semantic Search
├── OCR
└── Recommendations

Platform
├── Desktop
├── Mobile
├── Web
└── Synchronization

## Архитектурные слои

На начальном этапе предполагается использовать многослойную архитектуру:

Presentation
      ↓
Application
      ↓
Domain
      ↓
Infrastructure

### Presentation

Отвечает за:

- пользовательский интерфейс;
- навигацию;
- взаимодействие с пользователем;
- платформозависимое представление.

### Application

Отвечает за:

- сценарии использования;
- координацию операций;
- прикладные процессы.

### Domain

Содержит основные понятия и бизнес-правила системы.

Примеры:

- Entity;
- Workspace;
- Relationship;
- Task;
- Project.

Domain не должен зависеть от UI-фреймворков или конкретных инфраструктурных технологий.

### Infrastructure

Отвечает за:

- базу данных;
- файловую систему;
- сеть;
- AI-провайдеров;
- синхронизацию;
- системные возможности платформы.

## Проектирование вокруг предметной области

Архитектура должна строиться вокруг понятий предметной области, а не вокруг экранов.

Например, Task существует не потому, что существует экран «Задачи».

Task является объектом предметной области и может использоваться:

- Dashboard;
- Workspace;
- Calendar;
- AI;
- Search;
- Automation.

## Правило зависимостей

Зависимости должны направляться внутрь системы:

Presentation
     ↓
Application
     ↓
Domain
     ↑
Infrastructure

Domain не должен зависеть от UI или конкретной реализации Infrastructure.

## Архитектура искусственного интеллекта

ИИ должен быть реализован как отдельный сервисный слой, а не встраиваться непосредственно в каждый функциональный модуль.

Предполагаемая архитектура:

LifeOS
   |
AI Service
   |
   ├── Local Models
   ├── Cloud Models
   ├── Embeddings
   ├── Semantic Search
   ├── Context Engine
   └── Tool Execution

Это позволит в будущем поддерживать различных AI-провайдеров.

## Владение данными

По умолчанию пользовательские данные должны храниться локально.

Архитектура должна предусматривать возможность синхронизации в будущем, но синхронизация не должна быть обязательным условием для базовой работы приложения.

## Текущий статус архитектуры

Этот документ описывает только первоначальное направление.

Следующие решения пока остаются открытыми:

- язык программирования;
- UI-фреймворк;
- движок базы данных;
- архитектура синхронизации;
- архитектура AI-провайдеров;
- система плагинов;
- стратегия шифрования.

Эти решения будут приниматься и фиксироваться через документы ADR — Architecture Decision Records (архитектурные записи решений).
