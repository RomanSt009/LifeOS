# Архитектура базы данных LifeOS

**Статус:** Черновик  
**Версия:** 0.1  
**Дата:** 2026-08-10

---
# 1. Назначение

Этот документ описывает физическую архитектуру хранения данных LifeOS.

Документ определяет:

- принцип Local First;
- основную локальную базу данных;
- файловое хранилище;
- Repository Layer;
- Sync Queue;
- индексацию;
- полнотекстовый поиск;
- будущий semantic search;
- резервное копирование;
- миграции;
- требования к производительности.

Конкретная SQL-схема будет определена на следующем этапе.

---

# 2. Основной принцип — Local First

LifeOS должен быть полноценным приложением без постоянного подключения к интернету.

Основная рабочая копия данных пользователя находится локально на устройстве.

```text
User
  ↓
LifeOS
  ↓
Local Database
  ↓
Local File Storage
````

Интернет является дополнительным сервисом, а не обязательным условием работы приложения.

---

# 3. Почему Local First

Local First позволяет:

- работать без интернета;
- уменьшить задержку операций;
- быстро открывать данные;
- сохранять данные даже при отсутствии сети;
- уменьшить зависимость от облачной инфраструктуры;
- повысить приватность;
- предоставить пользователю контроль над локальными данными.

---

# 4. Основная база данных

Предварительно выбирается:

**SQLite**

SQLite используется как основное локальное структурированное хранилище.

```
LifeOS
   │
   └── SQLite
        ├── Entities
        ├── Relationships
        ├── Tasks
        ├── Projects
        ├── Notes
        ├── Documents
        ├── People
        ├── Events
        └── System Data
```

Окончательный выбор SQLite будет подтверждён после технического прототипа.

---

# 5. Требования к базе данных

База должна обеспечивать:

- транзакции;
- атомарные изменения;
- индексацию;
- полнотекстовый поиск;
- миграции схемы;
- восстановление после ошибок;
- локальную работу;
- масштабирование количества сущностей;
- безопасное удаление;
- возможность синхронизации;
- поддержку резервного копирования.

---

# 6. Логическая и физическая модель

Логическая модель описана в:

`docs/03-database/data-model.md`

Физическая модель должна реализовать эту структуру без чрезмерной связанности приложения с конкретной БД.

```
Domain Model
      ↓
Repository
      ↓
Database Adapter
      ↓
SQLite
```

Domain Layer не должен напрямую зависеть от SQL-запросов.

# 8. Таблица Entities

`entities` является системным слоем всех сущностей.

Предварительно:

```
entities
├── id
├── type
├── created_at
├── updated_at
├── lifecycle_state
└── metadata
```

Она обеспечивает:

- уникальный ID;
- тип сущности;
- системные даты;
- жизненный цикл;
- общие метаданные.

Специализированные данные хранятся в соответствующих таблицах.

---

# 9. Специализированные таблицы

Для типов сущностей с уникальными свойствами используются специализированные таблицы.

Например:

```
entities
    │
    ├── tasks
    ├── projects
    ├── notes
    ├── people
    ├── events
    └── documents
```

Это позволяет сохранять строгую структуру данных.

Например, Task может иметь:

```
priority
status
due_at
completed_at
```

а Person:

```
name
phone
email
```

---

# 10. Relationships

Связи между сущностями хранятся отдельно.

Предварительно:

```
relationships
├── id
├── source_entity_id
├── target_entity_id
├── relationship_type
├── source
├── confidence
├── status
├── created_at
└── updated_at
```

Это позволяет создавать граф связей без необходимости добавлять большое количество специальных внешних ключей в каждую таблицу.

---

# 11. Индексация

Для часто используемых операций должны создаваться индексы.

Потенциально индексируются:

```
entity.id
entity.type
entity.lifecycle_state
entity.created_at
entity.updated_at

relationship.source_entity_id
relationship.target_entity_id
relationship.relationship_type

task.status
task.due_at

event.start_at
event.end_at
```

Окончательный набор индексов определяется после анализа реальных запросов.

Необходимо избегать избыточной индексации, поскольку индексы увеличивают размер базы и стоимость операций записи.

---

# 12. Полнотекстовый поиск

Для текстовых данных LifeOS должен поддерживать полнотекстовый поиск.

Предварительно рассматривается:

**SQLite FTS5**

FTS должен использоваться для поиска по:

- Notes;
- Tasks;
- Projects;
- Documents metadata;
- People;
- другим текстовым сущностям.

Пример:

```
Запрос:
"ремонт кухни"

        ↓

Full Text Search

        ↓

Relevant Entities
```

---

# 13. Обычный поиск и полнотекстовый поиск

Это разные механизмы.

### Обычный поиск

Используется для точных условий:

```
Task.status = active
```

или:

```
Event.start_at > today
```

### Full Text Search

Используется для текстового поиска:

```
"ремонт кухни"
```

Оба механизма должны использоваться совместно.

---

# 14. Semantic Search

В будущем LifeOS должен поддерживать семантический поиск.

Он позволяет искать не только совпадение слов, но и смысл.

Например:

```
Запрос:

"Где я писал о покупке материалов для кухни?"
```

Система может найти заметку:

```
"Нужно заказать плитку и затирку до пятницы."
```

даже если слово "материалы" в ней отсутствует.

---

# 15. Архитектура поиска

Будущая система поиска:

```
                    Search
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
      Exact Search             FTS
          │                       │
          └───────────┬───────────┘
                      ↓
              Semantic Search
                      ↓
               Result Ranking
                      ↓
             Relevant Entities
```

Semantic Search не является обязательной частью первого MVP.

Сначала должна быть реализована быстрая и надёжная обычная система поиска.

---

# 16. AI Context

Поисковая система не должна напрямую передавать результаты AI.

Между ними находится Context Engine.

```
User Request
     ↓
Search
     ↓
Candidate Entities
     ↓
Context Engine
     ↓
Relevant Context
     ↓
AI
```

Context Engine отвечает за:

- релевантность;
- ограничения количества данных;
- lifecycle;
- relationships;
- приоритет;
- разрешения;
- чувствительность данных.

---

# 17. Архивные данные

Архивные данные остаются в базе, но не должны автоматически попадать в обычный AI-контекст.

```
ACTIVE
   ↓
Context Engine
   ↓
AI

ARCHIVED
   ↓
обычно исключено
   ↓
доступно при явном запросе
```

Например:

```
"Что мне делать сегодня?"
```

не должно автоматически загружать архивный проект пятилетней давности.

Но:

```
"Что мы делали во время ремонта квартиры?"
```

может активировать поиск по архиву.

---

# 18. File Storage

Большие файлы не должны храниться непосредственно внутри SQLite без необходимости.

Предварительная структура:

```
LifeOS Data
│
├── database/
│   └── lifeos.db
│
└── files/
    ├── documents/
    ├── images/
    ├── audio/
    ├── video/
    └── other/
```

SQLite хранит metadata и ссылку на файл.

---

# 19. File Metadata

Для каждого файла могут храниться:

```
Document
├── id
├── filename
├── mime_type
├── size
├── checksum
├── storage_path
├── created_at
└── updated_at
```

Checksum может использоваться для проверки целостности и синхронизации.

---

# 20. File Sync

Файлы рассматриваются отдельно от синхронизации структурированных данных.

```
Data Sync
    +
File Sync
```

Причина:

текстовая заметка может занимать несколько килобайт, а видео — несколько гигабайт.

Механизмы передачи и хранения должны учитывать этот масштаб.

---

# 21. Sync Queue

Для будущей синхронизации локальная база должна иметь очередь изменений.

Предварительно:

```
sync_queue
├── id
├── entity_id
├── operation
├── payload
├── created_at
├── status
└── retry_count
```

Возможные операции:

```
CREATE
UPDATE
DELETE
```

---

# 22. Offline Operations

Когда устройство находится офлайн:

```
User
 ↓
LifeOS
 ↓
SQLite
 ↓
Sync Queue
```

Данные считаются сохранёнными сразу.

Sync Queue ожидает подключения.

После восстановления сети:

```
Sync Queue
     ↓
Sync Engine
     ↓
Cloud
```

---

# 23. Повторная отправка

Синхронизация должна быть устойчивой к временным ошибкам.

Например:

```
pending
   ↓
syncing
   ↓
failed
   ↓
retry
   ↓
synced
```

Количество повторных попыток и стратегия backoff будут определены позже.

---

# 24. Транзакции

Критические изменения должны выполняться атомарно.

Например создание Task и Relationship:

```
BEGIN TRANSACTION

Create Task
Create Relationship
Create Sync Operation

COMMIT
```

Если операция не завершилась:

```
ROLLBACK
```

Это предотвращает появление частично сохранённых данных.

---

# 25. Миграции

Структура базы будет изменяться по мере развития LifeOS.

Например:

```
Database v1
     ↓
Migration
     ↓
Database v2
     ↓
Migration
     ↓
Database v3
```

Миграции должны быть:

- версионированными;
- последовательными;
- тестируемыми;
- обратимо восстанавливаемыми через backup.

Нельзя изменять production-схему без миграции.

---

# 26. Backup

Пользователь должен иметь возможность создать локальную резервную копию.

Минимальный вариант:

```
LifeOS
   ↓
Backup
   ↓
Encrypted Archive
```

В будущем:

- автоматические backup;
- несколько поколений backup;
- восстановление отдельных сущностей;
- экспорт данных.

---

# 27. Экспорт данных

LifeOS должен придерживаться принципа:

> Пользователь не должен быть заперт внутри приложения.

Необходимо предусмотреть экспорт.

Потенциальные форматы:

```
JSON
Markdown
CSV
PDF
```

Конкретный набор будет определён позже.

Для полноценного резервного восстановления должен существовать собственный формат экспорта LifeOS.

---

# 28. Производительность

Основные требования:

- локальные операции должны выполняться быстро;
- интерфейс не должен блокироваться долгими операциями базы;
- поиск должен использовать индексы;
- тяжёлые операции должны выполняться асинхронно;
- большие файлы не должны загружаться целиком в память без необходимости;
- AI-запросы не должны блокировать UI.

---

# 29. Масштабирование

Первоначальная версия должна быть рассчитана на одного пользователя и локальное устройство.

При этом архитектура не должна препятствовать дальнейшему развитию:

```
MVP
 ↓
Desktop
 ↓
Mobile
 ↓
Cloud Sync
 ↓
Multiple Devices
```

SQLite остаётся локальным хранилищем каждого устройства.

Cloud становится механизмом синхронизации, а не заменой локальной базы.

---

# 30. Безопасность

База данных должна рассматриваться как чувствительное пользовательское хранилище.

В дальнейшем необходимо реализовать:

- шифрование локальной базы;
- защищённое хранение ключей;
- безопасное хранение файлов;
- защиту backup;
- контроль доступа AI;
- безопасную синхронизацию;
- управление доверенными устройствами.

Конкретная криптографическая архитектура будет описана отдельно в `sync-architecture.md`.

---

# 31. Принцип минимизации данных

LifeOS не должен хранить данные без необходимости.

Каждый тип данных должен иметь понятную причину существования.

Необходимо избегать:

- дублирования;
- бесконтрольного хранения временных данных;
- ненужных копий файлов;
- неограниченного кеширования;
- бессрочного хранения промежуточных AI-данных.

---

# 32. Кэш

Кэш не должен считаться основной копией данных.

```
Source of Truth
      ↓
SQLite / File Storage
```

Кэш может быть удалён и восстановлен.

Это важно для предотвращения накопления "мёртвых" данных.

---

# 33. AI-временные данные

AI может создавать:

- embeddings;
- промежуточные результаты;
- классификации;
- предложения;
- summaries.

Такие данные должны иметь собственный lifecycle.

Например:

```
Generated
   ↓
Useful
   ↓
Stale
   ↓
Regenerate / Delete
```

AI не должен бесконтрольно создавать постоянные копии пользовательских данных.

---

# 34. Источник истины

Для локального приложения:

```
SQLite + File Storage
```

являются основным источником истины.

AI-кэш, поисковый индекс и синхронизационный кэш не являются источником истины.

```
              Source of Truth
                     │
              ┌──────┴──────┐
              ↓             ↓
           SQLite       File Storage
              │
       ┌──────┴───────┐
       ↓              ↓
   Search Index    AI Index
       │              │
       └──────┬───────┘
              ↓
             Cache
```

Если индекс повреждён, его можно построить заново из основной базы.

```
                            │

                            │

                            │

                            │

```

---

# 36. Архитектурные принципы

На текущем этапе зафиксированы:

1. LifeOS — Local First.
2. SQLite является предварительным выбором локальной БД.
3. Файлы хранятся отдельно от структурированных данных.
4. Repository изолирует Domain от SQLite.
5. Sync Engine является отдельным слоем.
6. Offline работа является обязательной.
7. Sync Queue используется для накопления изменений.
8. Search и AI Context являются отдельными подсистемами.
9. AI не является источником истины.
10. Архивные данные не входят в обычный AI-контекст.
11. Кэш можно восстановить из источника истины.
12. Структура базы изменяется только через миграции.
13. Пользователь должен иметь возможность экспортировать свои данные.
14. Безопасность и шифрование являются обязательными архитектурными требованиями.
15. Cloud Sync не должен быть обязательным условием работы LifeOS.
