# Модель данных LifeOS

**Статус:** Черновик  
**Версия:** 0.1  
**Последнее обновление:** 2026-08-09

## 1. Назначение

Этот документ определяет логическую модель данных LifeOS.

Он описывает:

- основные сущности;
- общие свойства сущностей;
- связи между сущностями;
- жизненный цикл данных;
- AI-предложения связей;
- правила удаления и архивирования;
- принципы владения и контекста данных.

Документ не определяет конкретную реализацию базы данных.

Физическая структура базы данных будет спроектирована отдельно после утверждения логической модели.

---

# 2. Основной принцип

LifeOS строится вокруг сущностей и связей между ними.

Основная идея:

> **Сущность существует самостоятельно. Связи добавляют ей контекст, но не определяют её существование.**

Например:

```text
Task
└── "Позвонить маме"
````

является полноценной задачей даже без:

- Workspace;
- Project;
- Person;
- Event.

Позже к ней могут быть добавлены связи.

```
Task
├── related_to → Person
├── belongs_to → Project
└── scheduled_for → Event
```

Это позволяет пользователю быстро создавать информацию без необходимости сначала создавать сложную структуру.

---

# 3. Entity

Entity — базовое понятие LifeOS.

Entity представляет любой значимый объект, которым система может управлять.

## Первоначальные типы Entity

Для MVP определяются следующие типы:

```
Workspace
Project
Task
Note
Document
Person
Event
```

Будущие типы:

```
Expense
Goal
Habit
Bookmark
Place
JournalEntry
Media
Automation
```

Новые типы могут добавляться по мере развития системы.

---

# 4. Общие свойства Entity

Каждая сущность должна иметь общий набор системных свойств.

```
Entity
├── id
├── type
├── title
├── description
├── created_at
├── updated_at
├── lifecycle_state
└── metadata
```

## ID

Уникальный идентификатор сущности.

ID не должен зависеть от названия или содержимого объекта.

Предпочтительно использовать UUID или другой устойчивый уникальный идентификатор.

## Type

Тип сущности.

Примеры:

```
task
note
project
person
document
event
workspace
```

## Title

Краткое название сущности.

Например:

```
Купить плитку
```

## Description

Дополнительное текстовое описание.

Поле может быть пустым.

## Created At

Дата и время создания.

## Updated At

Дата и время последнего изменения.

## Lifecycle State

Состояние жизненного цикла сущности.

Начальная модель:

```
active
inactive
archived
trash
deleted
```

`deleted` может существовать только как логическое состояние до окончательного физического удаления.

## Metadata

Дополнительные системные или расширяемые данные.

Использование Metadata не должно превращать её в неконтролируемое хранилище основных данных.

---

# 5. Workspace

Workspace представляет контекст или область жизни пользователя.

Примеры:

```
Личная жизнь
Работа
Ремонт квартиры
Обучение
Автомобиль
```

Workspace не является владельцем содержащихся в нём сущностей.

Он является контекстом.

## Основные свойства

```
Workspace
├── id
├── title
├── description
├── icon
├── lifecycle_state
└── settings
```

---

# 6. Project

Project представляет конкретную деятельность или инициативу, которая обычно имеет определённый результат.

Примеры:

```
Ремонт кухни
Создание LifeOS
Подготовка к экзамену
Запуск бизнеса
```

Project может быть связан с:

- Task;
- Note;
- Document;
- Person;
- Event;
- Workspace.

Project не обязан принадлежать Workspace.

Он может существовать самостоятельно.

---

# 7. Task

Task представляет действие, которое пользователь хочет выполнить.

Пример:

```
Купить плитку
```

## Основные свойства

```
Task
├── id
├── title
├── description
├── status
├── priority
├── due_at
├── completed_at
├── created_at
└── updated_at
```

## Status

Первоначальная модель:

```
todo
in_progress
completed
cancelled
```

В будущем модель может быть расширена.

## Priority

Первоначально:

```
low
normal
high
urgent
```

Task может существовать без Project.

---

# 8. Note

Note представляет свободную информацию.

Пример:

```
Для кухни нужна плитка 60×60.
```

Note может содержать:

- текст;
- ссылки;
- изображения;
- вложения;
- ссылки на другие сущности.

Note может существовать самостоятельно.

---

# 9. Document

Document представляет файл или ссылку на внешний ресурс.

Примеры:

```
Договор.pdf
Смета.xlsx
Инструкция.pdf
Фото кухни.jpg
```

В базе данных предпочтительно хранить не сам большой бинарный файл, а его метаданные и ссылку на физическое расположение.

```
Document
├── id
├── title
├── file_reference
├── mime_type
├── file_size
├── checksum
└── metadata
```

Фактическое хранение файлов будет определено архитектурой файлового хранилища.

---

# 10. Person

Person представляет человека.

Пример:

```
Иван Петров
```

Потенциальные данные:

```
Person
├── id
├── name
├── phone
├── email
├── notes
└── metadata
```

Контактные данные не являются обязательными.

Person может существовать независимо от Workspace и Project.

---

# 11. Event

Event представляет событие, связанное со временем.

Пример:

```
Встреча с Иваном
15 августа
14:00
```

Основные свойства:

```
Event
├── id
├── title
├── description
├── start_at
├── end_at
├── location
└── metadata
```

Event может быть связан с:

- Person;
- Project;
- Task;
- Workspace.

---

# 12. Relationship

Relationship — связь между двумя сущностями.

Общая модель:

```
Relationship
├── id
├── source_entity_id
├── target_entity_id
├── relationship_type
├── source
├── confidence
├── status
├── created_at
└── updated_at
```

## Source Entity

Сущность, из которой исходит связь.

## Target Entity

Сущность, на которую указывает связь.

## Relationship Type

Тип связи.

Примеры:

```
belongs_to
related_to
mentions
works_on
assigned_to
scheduled_for
references
contains
depends_on
```

Набор типов связей будет развиваться.

---

# 13. Источник связи

Каждая связь должна иметь информацию о том, каким способом она была создана.

```
source
├── manual
├── ai
├── imported
└── system
```

## Manual

Связь создал пользователь.

## AI

Связь предложил или создал AI.

## Imported

Связь появилась в результате импорта данных.

## System

Связь создана внутренними правилами LifeOS.

---

# 14. AI Relationship Workflow

AI не должен безусловно изменять структуру данных пользователя.

Основной процесс:

```
Entity
   ↓
Context Analysis
   ↓
AI обнаруживает возможную связь
   ↓
Relationship Suggestion
   ↓
Пользователь
   ├── Accept
   ├── Edit
   └── Reject
```

---

# 15. Статусы AI-связей

Предлагается использовать:

```
suggested
confirmed
rejected
```

## Suggested

AI предполагает существование связи.

Она ещё не считается подтверждённой пользователем.

## Confirmed

Связь подтверждена пользователем.

## Rejected

Пользователь отклонил предложение.

Отклонённые связи могут использоваться системой для улучшения будущих предложений.

---

# 16. Confidence

AI-предложение может иметь уровень уверенности.

Например:

```
confidence = 0.94
```

Это означает высокую вероятность того, что связь релевантна.

Confidence используется для сортировки и принятия решений интерфейсом.

Например:

```
94% → показать как сильное предложение

63% → показать как возможную связь

21% → возможно не показывать пользователю
```

Пороговые значения будут определены после появления реального AI-модуля.

---

# 17. Ручное редактирование

Пользователь всегда должен иметь возможность:

- подтвердить связь;
- отклонить связь;
- удалить связь;
- изменить тип связи;
- изменить связанную сущность;
- создать связь вручную.

AI не должен блокировать ручное управление.

---

# 18. Жизненный цикл данных

Каждая сущность имеет состояние жизненного цикла.

```
ACTIVE
   ↓
INACTIVE
   ↓
ARCHIVED
   ↓
TRASH
   ↓
DELETED
```

Переходы могут происходить как вручную, так и с помощью автоматизированных предложений.

---

# 19. Active

Активные данные используются в повседневной работе.

Они могут участвовать в:

- Dashboard;
- поиске;
- AI Context;
- автоматизациях;
- уведомлениях.

---

# 20. Inactive

Данные временно не используются активно, но всё ещё имеют практическую ценность.

Они остаются доступными для поиска и могут быть возвращены в Active.

---

# 21. Archived

Архивные данные сохраняются, но исключаются из обычного рабочего контекста.

Например:

```
Ремонт квартиры 2026
        ↓
     Archived
```

Архивные данные не должны автоматически попадать в каждый AI-запрос.

Однако они должны быть доступны по запросу.

---

# 22. Trash

Удалённые пользователем данные сначала могут попадать в корзину.

Это позволяет:

- восстановить ошибочно удалённые данные;
- избежать случайной потери информации;
- реализовать период хранения перед окончательным удалением.

---

# 23. Deleted

После окончательного удаления данные могут быть физически удалены.

Для критических операций удаления необходимо предусмотреть защиту от случайной потери.

Механизм окончательного удаления будет определён отдельно.

---

# 24. Context и AI

LifeOS не должен передавать AI всю базу данных при каждом запросе.

Вместо этого используется Context Engine.

```
User Request
     ↓
Context Analysis
     ↓
Search
     ↓
Relevant Entities
     ↓
Relevant Relationships
     ↓
Context Assembly
     ↓
AI
```

Например:

```
Пользователь:

"Что мне нужно сделать сегодня?"
```

Система может выбрать:

```
Сегодня
│
├── Tasks
├── Events
├── Deadlines
├── Active Projects
└── Relevant Notes
```

Архивные данные не используются без необходимости.

---

# 25. Принцип минимального AI-контекста

AI должен получать только тот объём данных, который необходим для выполнения конкретной задачи.

Это обеспечивает:

- производительность;
- приватность;
- снижение стоимости AI-запросов;
- снижение количества нерелевантной информации;
- повышение качества ответов.

---

# 26. Удаление Workspace

Workspace не является владельцем своих сущностей.

Поэтому удаление Workspace не должно автоматически означать удаление связанных сущностей.

При удалении Workspace LifeOS должен предложить пользователю варианты:

```
Удалить Workspace

Что сделать со связанными данными?

[ Архивировать ]
[ Перенести ]
[ Оставить без Workspace ]
[ Удалить ]
[ Отмена ]
```

Удаление критически важных данных должно требовать дополнительного подтверждения.

---

# 27. Пример

Пользователь создаёт:

```
Workspace
└── Ремонт квартиры

Project
└── Ремонт кухни

Task
└── Купить плитку

Person
└── Иван

Note
└── Плитка 60×60

Document
└── Смета.pdf
```

Связи:

```
Project
├── related_to → Workspace
├── has_task → Task
├── related_to → Person
├── related_to → Note
└── related_to → Document
```

Если Workspace архивируется:

```
Workspace → ARCHIVED
```

остальные сущности не обязаны становиться архивными.

Их жизненный цикл управляется отдельно.

# 28. Основные принципы модели

На текущем этапе зафиксированы следующие принципы:

### Принцип 1

Сущность может существовать самостоятельно.

### Принцип 2

Связи добавляют контекст, но не определяют существование сущности.

### Принцип 3

AI может предлагать связи.

### Принцип 4

Пользователь сохраняет окончательный контроль над связями.

### Принцип 5

Подтверждённые пользователем связи не должны незаметно изменяться AI.

### Принцип 6

Данные имеют жизненный цикл.

### Принцип 7

Архивные данные сохраняются, но не участвуют в обычном AI-контексте.

### Принцип 8

AI получает только релевантный контекст, а не всю базу данных.

### Принцип 9

Workspace является контекстом, а не контейнером-владельцем данных.

### Принцип 10

Удаление и архивирование должны быть максимально безопасными и обратимыми до окончательного удаления.
