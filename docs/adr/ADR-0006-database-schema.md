# ADR-0006: Архитектура локальной базы данных LifeOS

**Статус:** Предварительно принято  
**Дата:** 2026-08-13  
**Версия:** 0.1

## Контекст

В ADR-0005 была принята Local-first архитектура LifeOS.

Основным локальным хранилищем выбрана:

- SQLite;
- Drift как типобезопасный слой доступа из Dart.

Следующим шагом необходимо определить концептуальную структуру базы данных.

LifeOS будет работать не только с задачами.

В системе должны храниться:

- сущности;
- связи;
- пользовательские данные;
- lifecycle;
- технические метаданные;
- данные синхронизации;
- потенциально AI-related metadata.

При этом структура базы должна оставаться расширяемой.

---

# 1. Основной принцип

База данных должна отражать Domain Model, но не становиться её точной копией.

Концептуальная схема:

```text
Domain
   ↓
Repository
   ↓
Drift
   ↓
SQLite
````

SQLite является инфраструктурным хранилищем.

Domain не должен зависеть от структуры SQL-таблиц.

---

# 2. Основные таблицы

На первом этапе предполагается следующий минимальный набор:

```
entities
relationships
sync_changes
```

Дополнительные таблицы появляются только при необходимости.

---

# 3. Entities

Основная таблица:

```
entities
```

Концептуально:

```
entities
├── id
├── type
├── data
├── created_at
├── updated_at
├── archived_at
├── deleted_at
└── version
```

---

# 4. Entity ID

Поле:

```
id
```

должно быть уникальным и стабильным.

ID не должен зависеть от:

- названия;
- позиции;
- UI;
- локального индекса;
- сервера.

Он должен сохраняться на протяжении жизненного цикла сущности.

---

# 5. Entity Type

Поле:

```
type
```

определяет тип сущности.

Например:

```
task
project
note
person
event
file
place
goal
```

Тип используется для:

- фильтрации;
- поиска;
- маршрутизации;
- отображения;
- AI Context;
- синхронизации.

---

# 6. Entity Data

На первом этапе необходимо сохранить баланс между типобезопасностью и расширяемостью.

Концептуально:

```
entities
├── id
├── type
├── data
└── metadata
```

Поле `data` может хранить специфические данные сущности в сериализованном формате.

Например:

```
{
  "title": "Подготовить презентацию",
  "priority": "high",
  "dueDate": "2026-08-15"
}
```

Однако Domain Model не должна работать напрямую с этим JSON.

Преобразование происходит на границе Infrastructure.

---

# 7. Почему не создавать отдельную таблицу для каждого типа сразу

Альтернативный подход:

```
tasks
projects
notes
people
events
...
```

имеет преимущества.

Но на раннем этапе он может привести к большому количеству миграций и таблиц.

LifeOS предполагает возможность появления новых типов сущностей.

Поэтому на первоначальном этапе используется более гибкая базовая модель.

---

# 8. Важное ограничение

Гибкость не должна превращать базу в:

```
Map<String, dynamic>
```

для абсолютно всех данных.

Если конкретное поле становится:

- часто используемым;
- критичным для поиска;
- важным для сортировки;
- важным для индексации;
- важным для запросов;

оно может быть вынесено в отдельное структурированное поле или таблицу.

---

# 9. Relationships

Связи хранятся отдельно.

Таблица:

```
relationships
```

Концептуально:

```
relationships
├── id
├── source_entity_id
├── target_entity_id
├── type
├── created_at
├── updated_at
├── deleted_at
└── metadata
```

---

# 10. Source и Target

Каждая связь имеет:

```
source_entity_id
target_entity_id
```

Например:

```
Task
 ↓
Project
```

может быть представлено:

```
source = Task ID
target = Project ID
type = belongs_to
```

---

# 11. Индексы Relationships

Так как связи являются центральной частью LifeOS, необходимо индексировать:

```
source_entity_id
target_entity_id
type
```

Это позволит эффективно выполнять запросы:

```
Какие связи есть у этой сущности?
```

и:

```
Какие сущности связаны с этим проектом?
```

---

# 12. Lifecycle

Для сущностей необходимо поддерживать lifecycle.

Предварительно:

```
created_at
updated_at
archived_at
deleted_at
```

Например:

```
archived_at = NULL
deleted_at = NULL
```

означает активную сущность.

---

# 13. Soft Delete

Удаление по умолчанию является логическим.

Вместо:

```
DELETE FROM entities
```

используется:

```
deleted_at = timestamp
```

Это позволяет:

- восстанавливать данные;
- синхронизировать удаления;
- обнаруживать изменения;
- разрешать конфликты.

---

# 14. Relationships и Soft Delete

Связи также должны поддерживать lifecycle.

Если связь удаляется:

```
relationship.deleted_at
```

может содержать timestamp.

Это позволяет синхронизировать удаление связи между устройствами.

---

# 15. Version

Для сущностей может использоваться:

```
version
```

Версия увеличивается при изменении сущности.

Например:

```
1
↓
2
↓
3
```

Version может использоваться Sync Engine для определения изменений.

---

# 16. Sync Changes

Для Local-first архитектуры требуется отслеживать локальные изменения.

Предварительная таблица:

```
sync_changes
```

Концептуально:

```
sync_changes
├── id
├── entity_id
├── operation
├── created_at
├── device_id
├── version
└── payload
```

В дальнейшем структура может измениться после проектирования полноценного Sync Engine.

---

# 17. Operation

Возможные операции:

```
create
update
delete
```

В будущем могут появиться:

```
archive
restore
relationship_create
relationship_delete
```

---

# 18. Sync Status

Не рекомендуется хранить всю синхронизационную логику непосредственно в Domain Entity.

Например:

```
Task
```

не должен превращаться в:

```
Task
├── title
├── status
├── syncStatus
├── syncRetryCount
├── syncError
├── syncServerVersion
└── ...
```

Sync metadata должна быть максимально изолирована.

---

# 19. Database Migrations

Структура SQLite будет изменяться по мере развития LifeOS.

Например:

```
Version 1
    ↓
Version 2
    ↓
Version 3
```

Каждое изменение схемы должно сопровождаться миграцией.

Миграции должны быть:

- последовательными;
- тестируемыми;
- обратимо документированными;
- совместимыми с существующими пользовательскими данными.

---

# 20. Никогда не удалять пользовательские данные ради миграции

Миграция:

```
Database v1
 ↓
Database v2
```

не должна означать:

```
DELETE DATABASE
CREATE NEW DATABASE
```

если это не является специально предусмотренным восстановлением.

Существующие пользовательские данные должны сохраняться.

---

# 21. Индексация

Индексы добавляются только для реальных сценариев запросов.

Например:

```
entities.type
entities.updated_at
relationships.source_entity_id
relationships.target_entity_id
```

Но нельзя создавать индексы на каждое поле заранее.

Избыточные индексы:

- увеличивают размер базы;
- замедляют записи;
- усложняют миграции.

---

# 22. Search

На первом этапе обычный поиск может использовать SQL.

В дальнейшем может быть добавлен:

```
SQLite FTS
```

для полнотекстового поиска.

AI/semantic search является отдельным уровнем.

```
SQL Search
    +
Full Text Search
    +
Semantic Search
```

---

# 23. Attachments

Файлы и большие бинарные данные не должны автоматически храниться непосредственно в основной таблице `entities`.

Предварительно:

```
attachments
├── id
├── entity_id
├── file_name
├── mime_type
├── size
├── path
└── created_at
```

Сам файл может находиться в файловой системе.

SQLite хранит метаданные и ссылку.

---

# 24. Почему не хранить большие файлы в SQLite

Основная база должна оставаться компактной.

Большие:

- изображения;
- видео;
- документы;
- аудио;

могут значительно увеличивать размер SQLite.

Поэтому предпочтительно:

```
SQLite
  ↓
metadata
  ↓
File System
  ↓
Actual File
```

---

# 25. Transactions

Операции, изменяющие несколько связанных объектов, должны использовать транзакции.

Например:

```
Create Project
+
Create Relationship
+
Create initial Note
```

может быть выполнено как одна транзакция.

Если операция не завершилась:

```
Rollback
```

необходимо избежать частично сохранённого состояния.

---

# 26. Referential Integrity

Relationships должны ссылаться на существующие entities.

Концептуально:

```
relationships.source_entity_id
        ↓
entities.id
```

и:

```
relationships.target_entity_id
        ↓
entities.id
```

Необходимо учитывать soft delete и sync scenarios при проектировании foreign keys.

---

# 27. Database as Infrastructure

SQL-запросы не должны распространяться по приложению.

Не:

```
Widget
 ↓
SQL
```

и не:

```
Domain
 ↓
SQL
```

а:

```
Repository
 ↓
Drift
 ↓
SQLite
```

---

# 28. Drift

Drift является типобезопасным слоем доступа к SQLite.

Он отвечает за:

- таблицы;
- запросы;
- транзакции;
- миграции;
- mapping;
- reactive queries.

Domain не должен напрямую зависеть от Drift API.

---

# 29. Backup

Backup базы является отдельной задачей.

Нельзя считать:

```
sync_changes
```

резервной копией.

Backup должен позволять восстановить пользовательские данные.

---

# 30. Encryption

Шифрование базы не принимается окончательно в этом ADR.

Это будет рассмотрено в:

```
ADR-0010: Security Architecture
```

Однако архитектура должна предусматривать возможность безопасного хранения пользовательских данных.

---

# 31. Database Size

LifeOS потенциально может хранить большое количество:

- сущностей;
- связей;
- заметок;
- истории;
- metadata.

Поэтому необходимо учитывать:

- индексацию;
- очистку временных данных;
- архивирование;
- pagination;
- query optimization.

Но преждевременная оптимизация не требуется.

---

---

# 33. Что является частью MVP

Для первого MVP достаточно:

```
entities
relationships
```

и минимальной инфраструктуры для:

```
created_at
updated_at
deleted_at
```

Sync tables не должны усложнять MVP до появления реальной синхронизации.

---

# 34. Что НЕ реализуем сейчас

Не создаём заранее:

- сложную event sourcing систему;
- graph database;
- распределённую базу;
- сложный CRDT;
- несколько database engines;
- сложную систему версионирования каждого поля;
- AI-specific database;
- отдельную vector database.

Эти технологии могут появиться позднее, если возникнет реальная необходимость.

---

# 35. Vector Storage

AI в будущем может использовать embeddings.

Но embeddings не должны автоматически становиться частью основной Entity таблицы.

Возможная будущая архитектура:

```
Entities
    ↓
Embedding Pipeline
    ↓
Vector Index
```

Конкретная технология будет определена отдельным ADR.

---

# 36. Основные принципы

Для базы данных LifeOS принимаются следующие правила:

1. SQLite является локальным основным хранилищем.
2. Drift является основным Dart-слоем доступа к SQLite.
3. Domain не зависит от SQLite или Drift.
4. Entities являются основными объектами хранения.
5. Relationships являются самостоятельной таблицей.
6. Soft Delete используется для пользовательских данных.
7. Sync metadata отделяется от Domain Model.
8. Миграции являются обязательными.
9. Пользовательские данные не удаляются при обычных миграциях.
10. Индексы добавляются по реальным сценариям.
11. Большие файлы не хранятся непосредственно в основной Entity таблице.
12. Multi-entity операции используют транзакции.
13. Search развивается постепенно.
14. Vector storage откладывается.
15. Graph database не используется на первом этапе.

# 37. Последствия решения

## Положительные

- простая базовая структура;
- хорошая расширяемость;
- поддержка Local-first;
- удобная интеграция Drift;
- возможность построения графа;
- возможность синхронизации;
- возможность полнотекстового поиска;
- возможность последующего AI/semantic search.

## Отрицательные

- гибкая Entity-модель требует дополнительных преобразований;
- Relationships усложняют запросы;
- миграции требуют дисциплины;
- Sync требует дополнительной metadata;
- при росте базы потребуется оптимизация запросов.

# Итог

LifeOS использует SQLite как локальное основное хранилище.

Минимальная концептуальная модель:

```
Entities
    +
Relationships
    +
Lifecycle
```

Дополнительная инфраструктура:

```
Sync
Backup
Search
AI
```

добавляется поверх этой основы.

Основной принцип:

> **База данных должна быть простой и надёжной в основании, а сложность должна добавляться только тогда, когда она решает конкретную проблему продукта.**

```

### И маленькое уточнение по AI

Я специально **не добавил конкретную модель в ADR-0006**. Это правильно сделать позже, в `ADR-0008 AI Provider Architecture`.

На сегодняшний день разумнее зафиксировать **архитектурный контракт**, а не, например, «LifeOS использует модель X». Тогда через год мы сможем заменить модель без изменения архитектуры приложения.

И ещё я бы не торопился с локальной моделью. **В MVP — API; архитектурно сразу оставляем возможность Local AI.** Когда дойдём до AI-прототипа, уже на реальных задачах LifeOS сравним качество, скорость, стоимость и требования к железу и выберем конкретные модели.
```
