# ADR-0023: Начальное хранение Entity и решения по Outbox

**Статус:** Принято  
**Дата:** 2026-09-06  
**Версия:** 0.1

## 1. Контекст

ADR-0016 определил общий Domain-контракт Entity. ADR-0017, ADR-0019 и ADR-0020 определили границы Persistence, модель изменений и логическую структуру SQLite. ADR-0021 выбрал Drift как предпочтительный Flutter Persistence Stack, а ADR-0022 закрепил расположение Infrastructure и направление зависимостей.

Перед первым Persistence-прототипом необходимо устранить неоднозначность между ранней рекомендацией ADR-0006 хранить специфичные данные Entity в сериализованном поле `entities.data` и более поздними решениями о разделении общего metadata и типизированных Domain-данных. Также необходимо зафиксировать минимальную форму Outbox, не реализуя удалённую синхронизацию.

---

## 2. Решение о физическом хранении Entity

Начальное Persistence-представление Entity использует гибридную реляционную структуру:

```text
entities
    ↓ общий обязательный Entity metadata

tasks / другие типизированные Domain tables
    ↓ специфичные поля конкретного типа Entity
```

Общая таблица `entities` хранит обязательные поля общего Entity-контракта, включая:

- стабильный Entity ID;
- Entity type;
- created at;
- updated at;
- lifecycle state;
- version;
- source.

Типизированные Domain-таблицы, например `tasks`, хранят только специфичные для соответствующей Entity данные. Типизированная запись ссылается на идентичность Entity из общей таблицы `entities`.

Для `Task` начальная типизированная таблица содержит только поля, необходимые текущей Domain-модели:

- ссылку на Entity ID;
- title;
- completion state.

Persistence Model остаётся отделённой от Domain Model. Drift-типы и SQLite-детали не должны попадать в Domain.

---

## 3. Отказ от начального `entities.data`

Для физического хранения Entity это решение и более поздние Persistence ADR заменяют первоначальную рекомендацию ADR-0006 хранить специфичное состояние Entity только в сериализованном поле `entities.data`.

Начальный Persistence-прототип не использует `entities.data` как единственное хранилище специфичных данных Entity. Специфичные данные размещаются в типизированных реляционных таблицах.

Это не запрещает сериализацию на других архитектурных границах, например для Outbox payload, импорта или внешних протоколов.

---

## 4. Атомарная локальная мутация и Outbox

Каждая локальная мутация синхронизируемой Entity должна атомарно записывать:

1. актуальный Domain State в Persistence Model;
2. соответствующую запись Outbox.

Обе записи выполняются в одной SQLite transaction:

```text
BEGIN
    Write Domain State
    Write Outbox Change
COMMIT
```

Если любая часть операции завершается ошибкой, вся transaction откатывается. Состояние, при котором Domain State сохранён без обязательной Outbox-записи, недопустимо.

Наличие таблицы и записей Outbox не означает, что Sync реализован. На этом этапе Outbox только надёжно фиксирует локальные изменения для будущей синхронизации.

---

## 5. Начальный формат Outbox payload

В начальном Persistence-прототипе Outbox payload представляет полный snapshot Entity после изменения.

Payload кодируется как JSON.

```text
Domain Entity
    ↓ full snapshot
JSON payload
    ↓
Outbox
```

Full snapshot выбран как минимальный понятный формат для восстановления состояния, диагностики и последующей разработки Sync-протокола.

Patch/delta payload и бинарные форматы на этом этапе не используются.

---

## 6. Change ID

Значение `change_id` предоставляется на границе Infrastructure через внедряемую зависимость или внедряемое значение, создающее ID.

Persistence implementation не должна быть жёстко связана с конкретной библиотекой генерации идентификаторов. Этот ADR не выбирает UUID/ULID package и не требует добавления такой зависимости.

Тестовые реализации должны использовать детерминированные значения `change_id`.

---

## 7. Device ID

Значение `device_id` передаётся через Infrastructure composition.

Полный production lifecycle идентичности устройства, включая создание, хранение, восстановление и регистрацию, откладывается до отдельного решения.

Persistence tests могут использовать фиксированный детерминированный `device_id`.

---

## 8. Drift generated code

Сгенерированные Drift-файлы `*.g.dart` включаются в систему контроля версий.

Они должны:

- создаваться только настроенным code generator;
- обновляться после изменения соответствующих исходных Drift declarations;
- проверяться вместе с остальным diff;
- никогда не редактироваться вручную.

---

## 9. Направление зависимостей

Сохраняется архитектурная цепочка:

```text
Presentation
    ↓
Application
    ↓
Domain Repository Interface
    ↑
Infrastructure Repository Implementation
    ↓
Drift
    ↓
SQLite
```

Database schema, Drift tables, Persistence Models, mapping и Repository implementations принадлежат Infrastructure. Repository interface и Domain Entity не зависят от Drift или SQLite.

---

## 10. Явно отложенные решения

На этом этапе не реализуются и не определяются окончательно:

- remote transport;
- Sync Worker;
- сервер или API;
- conflict resolution;
- регистрация устройств;
- полный production lifecycle `device_id`;
- patch/delta payload;
- бинарный payload;
- удалённое подтверждение и очистка Outbox;
- retry policy для сетевой синхронизации.

---

## 11. Приоритет решения

Если ADR-0023 конфликтует с ADR-0006 в вопросах физического хранения Entity или отложенного создания Outbox, для начальной Persistence implementation применяется ADR-0023.

В частности:

- вместо хранения специфичных данных только в `entities.data` используется гибрид `entities` + типизированные Domain-таблицы;
- обязательная Outbox-запись создаётся атомарно вместе с каждой локальной мутацией синхронизируемой Entity, даже несмотря на то, что удалённый Sync ещё не реализован.

Остальные решения ADR-0006 сохраняют силу там, где они не противоречат этому ADR и более поздним Persistence ADR.

---

## 12. Последствия решения

### Положительные

- устранена неоднозначность начальной структуры Entity storage;
- общие metadata и типизированные Domain-данные имеют разные ответственности;
- Domain остаётся независимым от Drift и SQLite;
- каждая локальная мутация надёжно фиксируется в Outbox;
- тесты могут быть детерминированными без выбора ID package;
- формат начального payload определён;
- политика хранения generated Drift code зафиксирована;
- будущим реализациям не требуется самостоятельно определять приоритет конфликтующих ранних рекомендаций.

### Отрицательные

- локальная запись требует transaction с несколькими таблицами;
- full JSON snapshot может занимать больше места, чем patch;
- Infrastructure должна выполнять явный mapping между Domain и Persistence Models;
- production device identity всё ещё требует отдельного решения.

---

## 13. Следующий шаг

Следующий технический шаг — минимальный Persistence vertical slice для `LifeOsTask`:

```text
LifeOsTask
    ↓
LifeOsTaskRepository
    ↓
Infrastructure Repository
    ↓
Drift transaction
    ├── entities
    ├── tasks
    └── outbox
    ↓
SQLite
```

Этот шаг проверяет локальное сохранение, загрузку, mapping и атомарное создание Outbox. Он не включает реализацию Sync.
