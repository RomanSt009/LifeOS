# ADR-0004: Архитектура сущностей Domain Model LifeOS

**Статус:** Предварительно принято  
**Дата:** 2026-08-13  
**Версия:** 0.1

## Контекст

LifeOS должен работать не только как список задач или заметок.

Основная идея системы — предоставить пользователю единое пространство для хранения информации и управления связями между ней.

В LifeOS могут существовать:

- задачи;
- проекты;
- заметки;
- люди;
- события;
- места;
- документы;
- файлы;
- цели;
- привычки;
- идеи;
- пользовательские сущности.

Эти объекты могут иметь связи друг с другом.

Например:

```text
Project
   ↓
Task
   ↓
Person
   ↓
Meeting
   ↓
Note
   ↓
File
````

Поэтому архитектура данных должна позволять создавать новые типы сущностей без полной переработки системы.

---

# Решение

LifeOS использует единую Domain Model, основанную на понятии **Entity**.

Сущность является самостоятельным объектом предметной области, имеющим:

- уникальный идентификатор;
- тип;
- состояние;
- жизненный цикл;
- метаданные;
- возможность иметь связи с другими сущностями.

---

# 1. Базовая Entity

Концептуально каждая сущность содержит:

```
Entity
├── id
├── type
├── createdAt
├── updatedAt
├── lifecycle
└── metadata
```

Дополнительные свойства определяются конкретным типом сущности.

Например:

```
Task
├── Entity fields
├── title
├── description
├── status
├── priority
└── dueDate
```

---

# 2. Entity ID

Каждая сущность должна иметь стабильный уникальный идентификатор.

ID не должен зависеть от:

- названия;
- позиции в списке;
- UI;
- локальной базы;
- сервера.

Например:

```
Task
id = 01J...
```

Идентификатор должен сохраняться при:

- изменении названия;
- перемещении;
- синхронизации;
- экспорте;
- импорте.

---

# 3. Entity Type

Каждая сущность имеет тип.

Например:

```
task
project
note
person
event
file
place
goal
```

Тип используется для:

- отображения;
- поиска;
- фильтрации;
- AI context;
- синхронизации;
- определения доступных действий.

---

# 4. Не все сущности одинаковы

Несмотря на общий базовый контракт, конкретные сущности могут иметь собственные свойства.

Например:

```
Task
```

может иметь:

```
status
priority
dueDate
completedAt
```

А:

```
Person
```

может иметь:

```
name
email
phone
company
```

Общий Entity контракт не должен заставлять все сущности иметь одинаковые поля.

---

# 5. Domain Entity vs Database Model

Domain Entity и Database Model не обязаны быть одним и тем же объектом.

```
Domain Entity
      ↓
Repository
      ↓
Database Model
      ↓
SQLite
```

Это позволяет менять структуру хранения данных, не изменяя бизнес-логику.

Например:

```
Task
```

в Domain может быть независим от того, хранится ли он:

- в SQLite;
- на сервере;
- в другом формате;
- в синхронизируемом хранилище.

---

# 6. Relationships

Связи являются отдельной частью модели.

Например:

```
Project
    │
    ├── contains → Task
    │
    ├── related → Person
    │
    └── references → Note
```

Связь не должна быть просто строковым полем внутри одной сущности.

Вместо:

```
Task.projectId
```

в архитектуре LifeOS должна существовать возможность представить связь:

```
Task
   ↓
Relationship
   ↓
Project
```

Это позволит в будущем поддерживать более сложные отношения.

---

# 7. Relationship Model

Концептуально:

```
Relationship
├── id
├── sourceEntityId
├── targetEntityId
├── type
├── strength
├── createdAt
├── updatedAt
└── metadata
```

Например:

```
source: Task
target: Project
type: belongs_to
```

или:

```
source: Note
target: Person
type: mentions
```

---

# 8. Направленные и ненаправленные связи

Некоторые связи имеют направление:

```
Task
  └── belongs_to → Project
```

Другие могут быть логически симметричными:

```
Person A
    ↕
Person B
```

Архитектура должна поддерживать оба сценария.

---

# 9. Типы связей

На раннем этапе не следует создавать сотни типов связей.

Предварительно можно использовать:

```
contains
belongs_to
related_to
references
depends_on
blocks
assigned_to
created_by
mentions
attached_to
```

Список будет расширяться только при появлении реальных сценариев.

---

# 10. Пользовательские связи

Пользователь должен иметь возможность создавать связи, которые не были заранее предусмотрены разработчиками.

Например:

```
"Этот проект связан с переездом"
```

Пользователь может создать:

```
Project
    ↓
related_to
    ↓
Move
```

Если тип связи допускает пользовательское название, система может сохранить:

```
relationshipLabel = "связан с переездом"
```

---

# 11. AI Generated Relationships

AI может предлагать связи.

Например пользователь создаёт:

> "Позвонить Ивану по поводу проекта X."

AI может предложить:

```
Task
 ↓
assigned_to
 ↓
Ivan

Task
 ↓
belongs_to
 ↓
Project X
```

Но AI не должен автоматически считать предложение подтверждённым пользовательским фактом без соответствующего разрешения.

---

# 12. Relationship Confidence

AI-предложение может иметь уровень уверенности.

Например:

```
confidence = 0.91
```

Но confidence не означает истинность.

Это только оценка AI.

Поэтому:

```
AI Suggestion
      ↓
User Review
      ↓
Accepted / Rejected
```

---

# 13. Lifecycle

Каждая сущность имеет жизненный цикл.

Предварительная модель:

```
Active
   ↓
Archived
   ↓
Deleted
```

Но физическое удаление из базы не обязательно происходит сразу.

---

# 14. Soft Delete

Для большинства сущностей предпочтительно использовать soft delete.

Например:

```
deletedAt = timestamp
```

Вместо немедленного:

```
DELETE FROM entities
```

Это позволит:

- восстанавливать данные;
- синхронизировать удаления;
- вести историю;
- предотвращать случайную потерю информации.

---

# 15. Архивирование

Архивирование отличается от удаления.

```
Active
  ↓
Archived
```

Архивная сущность:

- остаётся в системе;
- не обязательно показывается в обычных списках;
- может использоваться AI Context;
- может быть восстановлена.

---

# 16. Lifecycle и AI Context

Жизненный цикл напрямую влияет на контекст AI.

Например:

```
Active Task
    ↓
High relevance
```

а:

```
Deleted Task
    ↓
No context
```

Архивные данные могут иметь более низкий приоритет:

```
Archived
    ↓
Low relevance
```

Таким образом, lifecycle помогает контролировать объём контекста.

---

# 17. Entity Relevance

Не каждая сущность одинаково важна в каждый момент.

Для AI Context Engine может использоваться:

```
Relevance =
recency
+
relationship strength
+
user activity
+
lifecycle
+
explicit importance
```

Это не является окончательной математической формулой.

Это архитектурный принцип.

---

# 18. Entity Metadata

Общие технические метаданные могут включать:

```
createdAt
updatedAt
deletedAt
archivedAt
createdBy
updatedBy
version
```

Однако metadata не должна превращаться в универсальное место для хранения бизнес-логики.

---

# 19. Entity Extensions

Если конкретной сущности требуется дополнительная информация, она должна моделироваться явно.

Не рекомендуется превращать каждую сущность в:

```
Map<String, dynamic>
```

только ради гибкости.

Гибкость не должна уничтожать типобезопасность.

---

# 20. Custom Entities

В будущем LifeOS может поддерживать пользовательские типы сущностей.

Например:

```
UserEntityType
    ↓
"Travel"
```

с пользовательскими полями:

```
country
budget
departureDate
```

Однако Custom Entities не являются частью MVP.

Сначала система должна стабилизировать стандартную Domain Model.

---

# 21. Entity Graph

Связи между сущностями образуют граф.

Например:

```
                 Project
                /       \
               /         \
            Task         Person
             |             |
             |             |
           Note          Meeting
             |
            File
```

LifeOS может использовать этот граф для:

- поиска;
- навигации;
- AI Context;
- рекомендаций;
- автоматического обнаружения связей.

---

# 22. Graph не означает Graph Database

На первом этапе LifeOS не обязан использовать специализированную graph database.

Граф может быть представлен поверх SQLite:

```
Entities
    +
Relationships
```

Это позволяет начать с простой и зрелой технологии хранения.

---

# 23. Domain Services

Некоторые операции не принадлежат одной сущности.

Например:

```
RelationshipService
ContextService
RelevanceService
```

Такие операции могут быть реализованы как Domain Services.

---

# 24. Entity Rules

Domain должен определять правила сущностей.

Например:

```
Task
```

может иметь правило:

```
Completed Task
не может снова стать Active
```

если бизнес-логика проекта когда-нибудь потребует такого поведения.

Важно:

> Такие правила находятся в Domain, а не в UI и не в SQLite.

---

# 25. User Intent vs Entity

Пользователь может написать:

> "Позвони Ивану завтра."

AI может определить:

```
Intent:
Create Task
```

и предложить:

```
Task
title = "Позвонить Ивану"
dueDate = tomorrow
```

После подтверждения пользователя создаётся Domain Entity.

Таким образом:

```
Natural Language
       ↓
AI
       ↓
Intent
       ↓
User Confirmation
       ↓
Domain Entity
```

---

# 26. Entity Creation

Создание сущности должно происходить через Application Layer.

Не:

```
UI
 ↓
new Task()
 ↓
SQLite
```

а:

```
UI
 ↓
CreateTask
 ↓
Domain
 ↓
Repository
 ↓
Infrastructure
```

---

# 27. Entity Updates

Изменение сущности также должно проходить через Application Layer.

Например:

```
CompleteTask
UpdateProject
ArchiveNote
DeleteEntity
CreateRelationship
```

Это позволяет централизованно контролировать бизнес-правила.

---

# 28. Domain Model и AI

AI не является источником истины.

Источник истины:

```
Domain Model
     ↓
Repository
     ↓
Persistent Storage
```

AI может:

- предложить;
- классифицировать;
- связать;
- найти;
- суммировать;
- преобразовать.

Но AI не должен самостоятельно изменять Domain без прохождения Application Layer и соответствующих разрешений.

---

# 29. Domain Model и Sync

Sync также не является владельцем Domain Model.

```
Domain
  ↑
Repository
  ↑
Sync / Infrastructure
```

Синхронизация должна преобразовывать данные между локальным и удалённым представлением.

---

# 30. Основные принципы

Для Domain Model LifeOS принимаются следующие принципы:

1. Каждая сущность имеет стабильный ID.
2. Сущности имеют тип.
3. Сущности имеют жизненный цикл.
4. Связи являются самостоятельными объектами модели.
5. AI может предлагать связи, но не является источником истины.
6. Domain не зависит от инфраструктуры.
7. Database Model не обязана совпадать с Domain Entity.
8. Soft Delete предпочтительнее немедленного физического удаления.
9. Архивирование отличается от удаления.
10. Гибкость не должна уничтожать типобезопасность.
11. Graph-подход может быть реализован поверх SQLite.
12. Custom Entities откладываются до более позднего этапа.

---

# 31. Предварительная модель

```
                    Entity
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        Task        Project        Note
          │            │            │
          └────────────┼────────────┘
                       ↓
                 Relationship
                       │
                       ↓
                    Entity
```

Каждая сущность:

```
Entity
├── ID
├── Type
├── Lifecycle
├── Metadata
└── Domain-specific data
```

# 32. Последствия решения

## Положительные

- единая модель данных;
- возможность построения графа связей;
- удобная интеграция AI;
- возможность расширения типов сущностей;
- поддержка local-first;
- поддержка синхронизации;
- возможность восстановления удалённых данных;
- единый подход к бизнес-логике.

## Отрицательные

- модель сложнее обычного CRUD-приложения;
- потребуется продуманная система миграций;
- связи увеличивают сложность запросов;
- потребуется контроль количества и качества отношений;
- AI-generated relationships требуют механизма подтверждения.

---

# 33. Что пока не решаем

Следующие вопросы будут рассмотрены отдельно:

- точная схема SQLite;
- таблица Entities;
- таблица Relationships;
- индексы;
- versioning;
- conflict resolution;
- event sourcing;
- audit log;
- custom entities;
- AI confidence model;
- автоматическое удаление старых данных.

Эти решения не должны быть приняты до появления конкретных требований.

# Итог

LifeOS использует единую Domain Model, построенную вокруг сущностей и связей между ними.

Сущности имеют стабильный жизненный цикл и могут участвовать в графе взаимосвязей.

AI используется как интеллектуальный помощник, который может анализировать и предлагать изменения, но не является источником истины.

Основной принцип:

> **LifeOS хранит факты, AI помогает их понимать, а пользователь сохраняет контроль над значимыми изменениями.**

````

### Почему этот ADR сейчас особенно важен

Мы здесь заложили одну из главных идей LifeOS:

**не делать его просто «умным списком задач».**

У нас появляется модель:

```text
        ┌──────── Project
        │
        ↓
      Task ←──── Person
        │           │
        ↓           ↓
      Note ←──── Meeting
        │
        ↓
       File
````

А AI в дальнейшем сможет смотреть не на отдельную заметку, а на **релевантный фрагмент этого графа**.

И при этом мы не превращаем всю базу в бесконечную AI-память — это напрямую связано с нашим предыдущим решением **C+ (Context + Lifecycle)**.
