# ADR-0005: Local-first архитектура данных LifeOS

**Статус:** Предварительно принято  
**Дата:** 2026-08-13  
**Версия:** 0.1

## Контекст

LifeOS создаётся как персональная система управления информацией.

Пользователь должен иметь возможность работать с приложением независимо от наличия интернет-соединения.

На компьютере LifeOS должен позволять:

- создавать данные;
- изменять данные;
- просматривать данные;
- искать данные;
- создавать связи;
- работать с задачами;
- работать с проектами;
- работать с заметками;
- использовать базовые функции AI;
- просматривать историю и контекст.

Отсутствие интернета не должно превращать приложение в неработоспособную оболочку.

Поэтому архитектура должна быть построена вокруг принципа **local-first**.

---

# 1. Основной принцип

Основной принцип LifeOS:

> **Локальные данные являются первичным рабочим источником информации пользователя.**

Упрощённо:

```text
                    LifeOS
                       │
                       ↓
                 Local Database
                       │
                     SQLite
````

Интернет является дополнительным каналом:

```
Local Data
    ↕
Synchronization
    ↕
Remote Storage
```

а не обязательным промежуточным звеном.

---

# 2. Что означает Local-first

Local-first означает, что приложение в первую очередь работает с локальными данными.

Например:

```
Пользователь
    ↓
Создаёт задачу
    ↓
Application Layer
    ↓
SQLite
    ↓
Задача сохранена
```

Интернет при этом не требуется.

Если интернет доступен:

```
SQLite
   ↓
Sync Engine
   ↓
Remote Storage
```

данные могут быть синхронизированы.

---

# 3. Что не является Local-first

Не следует строить архитектуру:

```
UI
 ↓
Internet
 ↓
API
 ↓
Database
```

потому что при отсутствии сети:

```
Internet ❌
    ↓
Application ❌
```

становится недоступным.

Для LifeOS такой подход неприемлем.

---

# 4. Источник истины

На локальном устройстве источником истины для текущей рабочей сессии является:

```
SQLite
```

В нормальном offline-сценарии:

```
User
 ↓
LifeOS
 ↓
SQLite
```

не требуется удалённый сервер.

Однако в многосайтовой синхронизации понятие абсолютного единственного источника истины усложняется.

Поэтому:

> Локальная база является источником истины для локального устройства, а синхронизация отвечает за согласование нескольких копий данных.

---

# 5. Архитектура

Предварительная архитектура:

```
┌──────────────────────────────┐
│          User / UI           │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│        Application           │
│                              │
│ Commands / Queries           │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│           Domain             │
│                              │
│ Entities / Rules             │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│        Repository            │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│        SQLite / Drift        │
└──────────────┬───────────────┘
               │
               │
               ↓
┌──────────────────────────────┐
│         Sync Engine          │
└──────────────┬───────────────┘
               ↕
┌──────────────────────────────┐
│       Remote Storage         │
└──────────────────────────────┘
```

---

# 6. Write Path

При изменении данных основной путь:

```
User
 ↓
UI
 ↓
Application Command
 ↓
Domain
 ↓
Repository
 ↓
SQLite
```

После локального сохранения данные могут попасть в очередь синхронизации:

```
SQLite
 ↓
Sync Queue
 ↓
Sync Engine
 ↓
Remote
```

Главное:

> Успешная локальная запись не должна зависеть от успешной синхронизации.

---

# 7. Read Path

Чтение данных также происходит локально:

```
UI
 ↓
Query
 ↓
Repository
 ↓
SQLite
 ↓
UI
```

Даже при отсутствии интернета пользователь может:

- открыть проекты;
- просматривать задачи;
- искать заметки;
- смотреть связи;
- просматривать локальный AI-контекст.

---

# 8. Offline Mode

Offline не является отдельным аварийным режимом.

Для основной функциональности это нормальное состояние приложения.

```
Internet available
        ↓
Local-first

Internet unavailable
        ↓
Local-first
```

Меняется только возможность синхронизации и использования внешних сервисов.

---

# 9. Что происходит без интернета

Например пользователь создаёт:

```
"Подготовить презентацию"
```

без подключения к сети.

Процесс:

```
User
 ↓
CreateTask
 ↓
SQLite
 ↓
Task created
```

Пользователь сразу видит задачу.

Далее:

```
Internet unavailable
        ↓
Sync pending
```

Когда интернет появляется:

```
Internet restored
        ↓
Sync Engine
        ↓
Remote
```

---

# 10. Sync Queue

Для изменений, которые необходимо передать удалённому хранилищу, используется очередь синхронизации.

Концептуально:

```
Sync Queue
├── Create Task
├── Update Note
├── Create Relationship
└── Archive Project
```

Каждая операция имеет состояние.

Например:

```
Pending
    ↓
Syncing
    ↓
Synced
```

или:

```
Pending
    ↓
Failed
    ↓
Retry
```

---

# 11. Sync Metadata

Для синхронизации сущности могут иметь технические метаданные:

```
entityId
version
updatedAt
deviceId
syncStatus
```

Эти данные не являются частью пользовательского смысла сущности.

Они относятся к инфраструктуре синхронизации.

---

# 12. Local Changes

Каждое локальное изменение должно быть идентифицируемым.

Например:

```
Task updated
```

может породить:

```
Change
├── id
├── entityId
├── operation
├── timestamp
├── deviceId
└── payload
```

Это позволит Sync Engine определить, что именно необходимо отправить.

---

# 13. Не отправлять всю базу при каждой синхронизации

Система не должна постоянно делать:

```
SQLite
 ↓
Export entire database
 ↓
Upload
```

Вместо этого используется инкрементальная синхронизация.

```
Local Changes
      ↓
Sync Queue
      ↓
Remote Changes
```

Передаются только необходимые изменения.

---

# 14. Synchronization не должна блокировать UI

Плохой сценарий:

```
User changes Task
        ↓
Wait for internet
        ↓
Wait for server
        ↓
Show result
```

Правильный:

```
User changes Task
        ↓
Save locally
        ↓
Show result immediately
        ↓
Sync in background
```

---

# 15. Ошибки синхронизации

Если синхронизация не удалась:

```
Local Save
    ↓
Success
    ↓
Sync
    ↓
Failed
```

локальные данные не должны исчезать.

Например:

```
Task
status = active
syncStatus = pending
```

Пользователь продолжает работать.

---

# 16. Retry

Временные ошибки должны повторяться автоматически.

Например:

```
Failed
  ↓
Wait
  ↓
Retry
  ↓
Failed
  ↓
Wait longer
  ↓
Retry
```

Для повторных попыток может использоваться exponential backoff.

Конкретные параметры будут определены при проектировании Sync Engine.

---

# 17. Conflict

Конфликт возникает, когда одна сущность была изменена в нескольких местах.

Например:

```
PC:
Task title = "Подготовить презентацию"

Phone:
Task title = "Подготовить презентацию для клиента"
```

Оба устройства были offline.

После восстановления связи возникает конфликт.

Архитектура должна предусматривать механизм обнаружения таких ситуаций.

---

# 18. Не использовать бездумный Last Write Wins

Простое правило:

```
последнее изменение всегда побеждает
```

может привести к потере пользовательских данных.

Поэтому Last Write Wins не принимается как универсальная стратегия.

Для разных типов данных могут использоваться разные правила разрешения конфликтов.

---

# 19. Conflict Resolution

Предварительно возможны:

### Автоматическое разрешение

Если изменения не конфликтуют:

```
PC:
priority = high

Phone:
title = "Подготовить презентацию"
```

можно объединить изменения.

### Пользовательское разрешение

Если оба устройства изменили одно и то же поле:

```
PC:
title = "Презентация"

Phone:
title = "Презентация клиента"
```

пользователь может выбрать:

```
Use PC
Use Phone
Merge
```

---

# 20. AI и Offline

AI должен учитывать доступность сети.

Некоторые AI-функции могут работать локально.

Например:

```
Search
Classification
Basic context processing
```

Другие могут требовать внешний AI API:

```
Advanced generation
Cloud model
Remote embeddings
```

Если внешний AI недоступен:

```
AI unavailable
      ↓
Core LifeOS continues working
```

---

# 21. AI не должен быть критической зависимостью

Основные функции LifeOS не должны требовать AI.

Пользователь должен иметь возможность:

```
Create Task
Create Project
Create Note
Create Relationship
Search
Edit
Archive
Delete
```

без AI.

AI является дополнительным интеллектуальным слоем.

---

# 22. Local AI

В будущем может появиться:

```
Local AI Model
```

например для:

- классификации;
- поиска;
- извлечения сущностей;
- локального анализа;
- построения контекста.

Архитектура должна позволять подключать локальный AI без изменения Domain Model.

---

# 23. Data Ownership

Пользователь должен сохранять контроль над своими данными.

Локальные данные должны:

- храниться на устройстве;
- быть доступны пользователю;
- экспортироваться;
- восстанавливаться;
- не зависеть от конкретного облачного провайдера.

---

# 24. Export

Архитектура должна предусматривать экспорт данных.

Возможные форматы в будущем:

```
JSON
CSV
Markdown
ZIP / Backup
```

Конкретный формат будет определён отдельным решением.

---

# 25. Backup

Синхронизация не является полноценной заменой резервному копированию.

Необходимо различать:

```
Sync
```

и:

```
Backup
```

Sync:

> поддерживает несколько копий данных согласованными.

Backup:

> позволяет восстановить данные после потери или повреждения.

---

# 26. Local Database Backup

В будущем LifeOS должен поддерживать создание резервной копии локальных данных.

Например:

```
LifeOS
 ↓
Create Backup
 ↓
Encrypted Archive
```

Конкретная реализация будет определена позднее.

---

# 27. Security

Local-first не означает автоматически безопасный.

Необходимо учитывать:

- шифрование;
- доступ к локальным файлам;
- защиту резервных копий;
- API keys;
- credentials;
- удалённую синхронизацию;
- device authentication.

Security будет описана отдельным ADR.

---

# 28. Database as Application Boundary

SQLite не должна напрямую использоваться UI.

Правильная архитектура:

```
UI
 ↓
Application
 ↓
Repository
 ↓
Drift
 ↓
SQLite
```

Это позволяет изменить механизм хранения без изменения пользовательского интерфейса.

---

# 29. Caching

SQLite является основным локальным хранилищем.

Не следует создавать несколько независимых источников истины:

```
SQLite
+
Memory Cache
+
Local JSON
+
Temporary Database
```

без конкретной необходимости.

Кэш может существовать только как оптимизация.

Он не должен становиться вторым источником истины.

---

# 30. Performance

Local-first архитектура должна обеспечивать быстрый отклик интерфейса.

Основные операции:

```
Create
Read
Update
Search
```

должны выполняться локально.

Для больших объёмов данных будут использоваться:

- индексы;
- пагинация;
- оптимизированные запросы;
- фоновые операции;
- специализированный поиск.

---

# 31. Search

Базовый поиск должен работать локально.

Например:

```
User
 ↓
Search Query
 ↓
SQLite
 ↓
Results
```

В будущем может использоваться полнотекстовый поиск.

AI Search является дополнительным уровнем:

```
Traditional Search
        +
Semantic Search
        +
AI
```

---

# 32. Lifecycle

Local-first архитектура должна учитывать жизненный цикл сущностей.

Например:

```
Active
 ↓
Archived
 ↓
Deleted
```

Удалённые сущности могут некоторое время сохраняться локально для:

- восстановления;
- синхронизации удаления;
- разрешения конфликтов.

---

# 33. Device Identity

Для синхронизации устройство должно иметь стабильный технический идентификатор.

Например:

```
deviceId
```

Он используется для:

- определения источника изменения;
- разрешения конфликтов;
- диагностики;
- синхронизации.

Device ID не должен использоваться как пользовательский идентификатор.

---

# 34. Multi-device

В будущем пользователь может иметь:

```
PC
 ↓
LifeOS

Phone
 ↓
LifeOS

Tablet
 ↓
LifeOS
```

Все устройства работают локально.

```
PC Local DB
      ↕
   Sync
      ↕
Phone Local DB
```

---

# 35. Remote Storage

Удалённое хранилище не должно быть жёстко связано с Domain Model.

Например:

```
Sync Engine
    ↓
Remote Repository
```

а конкретный backend может измениться:

```
Provider A
Provider B
Self-hosted
Cloud
```

Без переписывания Domain.

---

# 36. Архитектурная схема

Итоговая модель:

```
                       LIFEOS
                          │
                          ↓
                  ┌───────────────┐
                  │  Application  │
                  └───────┬───────┘
                          ↓
                  ┌───────────────┐
                  │    Domain     │
                  └───────┬───────┘

                  ┌───────────────┐
                  │  Repository   │
                  └───────┬───────┘

                    Sync Engine
                          ↕
                  Remote Storage
```

# 37. Основные правила

Для Local-first архитектуры принимаются следующие правила:

1. Локальная база является основным рабочим источником данных устройства.
2. Интернет не требуется для основной работы приложения.
3. Запись сначала происходит локально.
4. Синхронизация выполняется отдельно.
5. Sync не блокирует UI.
6. Ошибка Sync не должна приводить к потере локальных данных.
7. Используется инкрементальная синхронизация.
8. Конфликты должны обнаруживаться.
9. Last Write Wins не используется как универсальное решение.
10. AI не является критической зависимостью.
11. Sync не является Backup.
12. SQLite остаётся инфраструктурной деталью.
13. Пользователь должен иметь возможность экспортировать свои данные.
14. Кэш не является вторым источником истины.
15. Архитектура должна поддерживать несколько устройств.

---

# 38. Что пока не решаем

Следующие вопросы требуют отдельных архитектурных решений:

- конкретный Sync Protocol;
- серверная архитектура;
- Remote Database;
- Conflict Resolution Algorithm;
- Encryption;
- Backup Format;
- Export Format;
- Device Authentication;
- Account System;
- Offline AI;
- Semantic Search;
- Full-text Search;
- Sync Queue Schema.

Эти вопросы не следует преждевременно объединять в один документ.

# 39. Последствия решения

## Положительные

- приложение работает без интернета;
- быстрый отклик;
- данные доступны локально;
- меньше зависимости от сервера;
- удобная работа на ноутбуке;
- естественная поддержка mobile;
- возможность фоновой синхронизации;
- возможность нескольких устройств;
- возможность локального AI.

## Отрицательные

- значительно сложнее синхронизация;
- появляются конфликты;
- требуется система миграций;
- необходимо хранить sync metadata;
- требуется продуманная backup-стратегия;
- больше кода инфраструктуры;
- сложнее тестирование multi-device сценариев.

# Итог

LifeOS строится как Local-first приложение.

Основная рабочая цепочка:

```
User
 ↓
Application
 ↓
Domain
 ↓
Repository
 ↓
SQLite
```

Синхронизация является дополнительным асинхронным процессом:

```
SQLite
 ↓
Sync Queue
 ↓
Sync Engine
 ↕
Remote Storage
```

Основной принцип:

> **Пользователь должен иметь возможность работать со своими данными даже тогда, когда интернет полностью отсутствует.**

````

### Что мы этим ADR закрепили

Теперь у нас складывается довольно цельная архитектура:

```text
                    LIFEOS
                       │
                       ▼
                 Flutter / UI
                       │
                       ▼
                 Application
                       │
                       ▼
                    Domain
                       │
                       ▼
                  Repository
                       │
                       ▼
                Drift / SQLite
                       │
                       ▼
                Локальные данные
                       │
                       ▼
                 Sync Queue
                       │
                       ▼
                 Sync Engine
                       ↕
                Облачное хранилище
````

И здесь есть важный архитектурный принцип, который я хочу сохранить на протяжении всего проекта:

**мы не будем сейчас проектировать сервер, синхронизацию и облако до последней детали.** Сначала строим правильное локальное приложение. Потом добавляем Sync как отдельный слой.
